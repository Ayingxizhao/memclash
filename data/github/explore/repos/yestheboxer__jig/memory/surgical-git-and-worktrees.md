**Use worktrees.** The repos in the workspace are **shared working checkouts that the user works in live**: they switch branches, commit, and rebase in the same tree. Isolate a task in a worktree rather than occupying the main checkout. Keep worktrees under the repo's `.worktrees/<name>` (or `.claude/worktrees/` when the harness creates them) and remove one once its branch has landed, because a stale worktree holding a branch will block a rebase of that stack.

The case that motivates it: only ONE writing agent can safely occupy a working tree, and switching branches underneath a live run corrupts its results. A worktree gives a second tree, so a second stream can proceed without touching the run in progress. Prefer a worktree over a disposable clone.

**Surgical git, everywhere, including worktrees.** Never run broad destructive git: no bare `git checkout -- .`, `git reset --hard`, or `git clean -fd`. Remove only your own files by explicit path (`rm path`, `git checkout -- <specific file>`). Before any git operation, check `git branch --show-current` and `git status`. If the branch or state is not what you expect, STOP and ask; the user may have taken the checkout. A single `git checkout -- .` plus `git clean -fd` can destroy the user's staged work on another branch.

**The shell cwd persists across Bash calls, and that persistence is a trap when a session touches two trees.** In one session, mid task in a worktree, a triage command started with `cd <main checkout> && gh api ...`. Every later command with relative paths then ran in the user's MAIN checkout: a `git fetch`, a lint diff whose changed file count belonged to a different branch, and finally `git merge origin/main` INTO the user's live branch, with conflict "resolutions" written into their files. Recovery worked only because their tree was clean and the hooks rejected the merge commit: `git checkout HEAD -- <the conflicted files>` then `git merge --abort` restored a clean status. The harness also sometimes resets cwd on its own, so the cwd is never trustworthy. The rules: (1) once a session works in a worktree, EVERY compound command that runs git or touches files starts with `cd <worktree> &&`, or uses `git -C <worktree>` and absolute paths, with no exceptions for read only triage; (2) `git merge` and `git commit` additionally require `pwd` and `git branch --show-current` printed in the SAME command, checked before trusting the result; (3) a surprising result (unknown commits in `git log`, a wrong changed file count, conflicts a prior check said cannot exist) means the tree is wrong, not the theory, so stop and print `pwd` before anything else. Also: a `Read` of a file can be silently mangled by an output compressing tool (it can show a conflicted file as clean); when two tools disagree about file content, trust the raw bytes from `od -c` or `sed -n`.

**The cwd rule covers edits and test runs, not only git.** A Python heredoc that patches a file, and the test run that "proves" it, both land in whichever worktree the previous Bash call `cd`ed into. The commit in the intended worktree then finds a clean tree, and the stray edit has to be reverted out of the other one by name. A `git merge-tree` can report one PR's conflicts as another's for the same reason. Every command in a session that touches more than one worktree starts with `cd <worktree> &&`, including Python edits, test runs, linters and grep. Parallel Bash calls in one batch share the cwd too, so each one carries its own `cd`.

**What a worktree does NOT isolate.** It gives a per worktree working directory, HEAD and index, and git refuses the same branch in two worktrees. Everything else is shared:

- **Refs.** `git rev-parse --git-common-dir` shows refs live in the shared `.git`. So `gh stack rebase` or `gh stack push` in one worktree rewrites branch refs another worktree has checked out. Run stack commands from ONE tree only (the `jig:principle-use-gh-stack-for-stacked-prs` skill).
- **Git hooks.** A hook manager that installs from a worktree can rewrite the SHARED `.git/hooks` to point at that worktree's virtualenv. When the worktree is removed, every checkout's hooks fail with "not found" until the hooks are reinstalled from the main checkout.
- **Local services.** Most suites are hermetic, but a handful open a real client and hit the same local database, workflow engine and cache whatever the worktree. Never run two real service suites at once.
- **External accounts.** A shared cloud sandbox or a hosted browser account collides across worktrees exactly as it does in CI.

An agent sandbox that cannot write `.git` makes concurrent commits a non issue, but the agent must still `cd` into the worktree before it starts (the `jig:principle-verify-delegated-work` skill).

**Always create a branch for any code change; never work directly on the base branch.** Check each repo's base branch rather than assuming it, and fetch first so the base is current. Use one consistent branch name prefix, for example `<your-handle>/slim-status-poll`. Creating the branch, pushing, and opening PRs is pre authorized (the `jig:principle-prs-create-freely-never-merge` skill).

**Commit style.** The user's words: "stop amending and force pushing. new commits are cleaner and let me say what changed in small bites. amend only when it makes sense." One clean initial commit for the branch's main change; after that, and especially once a PR exists, every follow up (review fixes, bot comment fixes) is a NEW small commit whose message says what changed. Amend only when it genuinely makes sense, for example a typo caught before the first push, or a branch that has never been pushed. The exception stacking forces: rebasing a stacked branch onto its updated base still requires a force push of the stacked branch (`gh stack sync` or `gh stack rebase`). That mechanic is fine; rewriting an already pushed commit's content via amend is what to avoid.

**This rule beats a repo or workspace CLAUDE.md that says "amend or squash so each branch carries exactly one commit".** Reading that line as licence to amend a commit that is already pushed and under bot review, then force pushing it, earns an immediate correction. Treat the one commit per branch line as applying to a branch that has NOT been pushed yet; once a PR exists, review fixes are new commits even when that leaves the branch with several.

**Cite a commit SHA only AFTER the rebase, never before.** Replying to ten review threads with two SHAs, then rebasing onto a base branch that had moved, rewrites both SHAs. Every link is dead on arrival and every comment has to be edited through `PATCH /repos/{o}/{r}/pulls/comments/{id}`. Push first, read the post rebase SHAs, then reply.

**A formatting pre commit hook makes the first commit after a formatting change fail.** The formatter rewrites the files and leaves the result unstaged, so `git commit` exits non zero by design and you re add and commit again. Chain the whole sequence with `&&`, not a mix of `&&` and `;`: a failed commit followed by a `;` chained push reports "Everything up-to-date", which reads exactly like success. If a hook runs a tool from a virtualenv that has gone missing, it dies with "not found"; rebuild the environment rather than skipping the hook. Never reach for `--no-verify`.

**Never chain `commit && push` (or a rebase or stack push) in one shell command.** Hooks reject commits, and a later step that still runs acts on the OLD state. One lint rejection can mean the commit never happens, the rebase aborts on a dirty index, and a stack push sends eight branches at their previous commit anyway. Commit as its own call, confirm the hook summary and that `git log -1` shows the new commit, THEN push.

**Grandfathered lint violations: fix only your own lines.** A changed lines lint hook can apply the repo's FULL config to changed lines only, so a file can be full of pre existing violations while your one added function is what fails. Fix only what you added; touching the older lines drags unrelated code into the PR diff.

**Never push to a colleague's branch.** Push only to your own branches. Stacking on a colleague's PR means rebasing YOUR branch onto theirs and setting your PR's base; it never means committing onto theirs. If their branch needs a change, even a revert of your own accident, draft the ask for the user to send them.

**Why:** worktrees keep agents off the user's live tree; small follow up commits let reviewers see what changed between looks; surgical git and a pinned cwd are the only things standing between a stray command and someone else's uncommitted work.

**How to apply:** put each task in a worktree under the repo's `.worktrees/<name>`. Start on a fresh branch with your prefix, cut from the repo's up to date base. Start every command with `cd <worktree> &&`. Follow ups are new commits with specific messages; pass this convention along in every coder brief too (the `jig:principle-verify-delegated-work` skill). Merging still needs the user. Related: [[background-work-must-be-tracked]].
