Coding agents such as Claude Code increasingly maintain their own memory. When a user corrects the agent, it writes a new rule, often as a separate file in a memory folder. Nothing checks a new rule against the existing ones, so memory accumulates contradictions, duplicates, and stale rules. In author's own setup, nine memory files and a 13-line CLAUDE.md already contain five such problems; one file even states both "~3" and "~5 sentences per idea." These problems matter because instruction compliance falls as rules accumulate (IFScale (opens in new tab)). The user pays by repeating the same correction.

Existing memory systems do not solve this problem because they treat memory as facts. Mem0 (opens in new tab) and Graphiti (opens in new tab) resolve conflicts between facts by keeping the newest value. Agent rules, however, are conditional: "use pip for Python installs" and "use uv for all code installs" share no key, yet conflict because their conditions overlap. Memory admission gates exist, but they either sample an LLM (ConsistencyGate (opens in new tab)) or remain unimplemented (SSGM (opens in new tab)). Policy-formalization work (AgentSpec (opens in new tab)) shows that LLMs can translate natural language into checkable policies, but only for fixed safety policies, not for preferences that grow over time.

I propose a deterministic consistency gate for agent memory. An LLM translates each new rule into a typed schema (scope, trigger, action, modality) adapted from access-control and deontic policy formalisms. A validator and the Z3 SMT solver then check whether the rule contradicts, duplicates, or overrides existing rules. A failed check returns a reason that the LLM uses to retry, mark an older rule as superseded, or ask the user. Rules that do not fit the schema are stored but marked unchecked. Unlike an LLM judge, the solver gives the same verdict every time and is exact with respect to the encoded rules.

I will answer four questions. How often do real memory folders contain conflicts (RQ0)? What fraction of rules fit the schema (RQ1)? How accurately does an LLM fill it (RQ2)? Does the solver detect conflicts more reliably than an LLM judge (RQ3)? Data comes from three sources: the author's own Claude Code memory and 79 session transcripts; public GitHub repositories that commit agent memory folders, found through code search (roughly 22,000 matching files); and synthetic rule sets with injected conflicts of known type. I compare against append-only memory and a Mem0-style LLM judge, using precision and recall on labelled conflicts.

The project will contribute, to my knowledge, the first measurement of conflict prevalence in agent memory, a runnable schema-and-solver prototype, and an analysis of where formal checking outperforms or loses to LLM judgment. A low coverage result would itself be informative, since it marks where formal methods stop being practical for agent memory.
